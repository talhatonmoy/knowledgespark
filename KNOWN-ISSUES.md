# KnowledgeSpark — Known Issues, Fixes, and Invariants

This file is the project's long-term memory for production issues that were solved.
**Read it before changing `includes/class-knowledgespark.php` or `assets/admin.js`.**
Each entry lists the user-visible symptom, root cause, the fix, the invariants future development
must respect, and the automated checks that will fail if a fix regresses.

## 1. AI call timed out at 45 s (`cURL error 28`, "AI ranking unavailable")

- **Symptom (user sees):** red/orange fallback: `AI ranking unavailable; showing semantic matches. cURL error 28: Operation timed out after 45006 milliseconds…` with boilerplate reasons and no anchors.
- **Root cause:** the provider (GLM-5.3-Flash via api.river.ai) needs ~30–90 s for the production prompt; the original generic 45 s HTTP timeout was too small.
- **Fix:** `rank()` passes a **120 s timeout** to the AI call only (Qdrant stays at 45 s), and `assets/admin.js` allows **180 s** for the `suggest` route (`var timeout = route === 'suggest' ? 180000 : 100000;`). The prompt was also slimmed to keep generation fast: article text 8,000 chars, 12 candidates × 1,500-char excerpts.
- **Invariants (do not regress):**
  - AI call timeout ≥ 120 s (`rank()`, the `...,120)` on the `request()` calls).
  - Browser suggest timeout ≥ server AI timeout + headroom (180 s in admin.js).
  - Prompt budget stays slim (8k / 12×1500) — the original 40k / 20×3500 payload pushed total time past any safe timeout.
- **Guards:** live-only (no mock); verify any AI-path change with a real run:
  `docker exec devkinsta_fpm php -r '<require wp-load, call KnowledgeSpark::api_suggest for post 410, print elapsed + message>'` — expect "AI-reviewed suggestions" in ~30–90 s, not the fallback.

## 2. "AI returned an invalid recommendation format" (thinking-model token truncation)

- **Symptom (user sees):** `AI ranking unavailable; showing semantic matches. AI returned an invalid recommendation format.` — even though the AI call *succeeded* (HTTP 200 in ~30–50 s). Intermittent.
- **Root cause:** GLM-5.3-Flash is a **thinking model**. It emits hidden chain-of-thought (`reasoning_content`; `usage.completion_tokens_details.reasoning_tokens`) that consumes output tokens. Observed reasoning lengths per identical call: **1,888 / 2,703 / 6,008 / 2,988 tokens**. With `max_tokens: 4000`, whenever reasoning exceeded the headroom the JSON answer was cut off mid-string (`finish_reason: length`) and `json_decode` failed. The provider **ignores** `thinking: {type: "disabled"}` (accepted, HTTP 200, reasoning still generated — probed 2026-11-21).
- **Fix (in `rank()` + `parse_rank_response()`):**
  - `max_tokens` raised **4,000 → 16,000** (the model emits the same reasoning either way; the cap only prevented truncation).
  - **One automatic retry** when the parse fails and the first attempt finished in < 90 s (truncation fails fast; reasoning length varies, so a retry usually gets a shorter one).
  - `parse_rank_response()` validates `choices[0].message.content` (string → strip optional ``` fence → `json_decode` → `suggestions` array).
  - Failure message is now self-diagnosing: `…(finish: length, completion tokens: 4000). The answer was cut off at the token limit. One automatic retry was attempted…`.
- **Invariants (do not regress):**
  - `max_tokens` ≥ ~8,000 (worse: never below what the longest observed reasoning + ~1,500 answer tokens needs).
  - Keep the retry-once + 90 s gate, and the diagnostics fields (`finish_reason`, `completion_tokens`) — they are the only way to see this class of failure from the UI.
  - Keep `parse_rank_response()` as the single parse/validation point for AI output.
- **Guards (tests/smoke.php):** `Retry the AI call once when it returns a truncated answer` and `Surface AI format failure with finish/token diagnostics` (mock hook `$GLOBALS['ks_format_fail']`).

## 3. Qdrant `cURL error 60: SSL: no alternative certificate subject name matches…`

- **Symptom (user sees):** suggestions died at the query step: `cURL error 60: SSL: no alternative certificate subject name matches target host name '…aws.cloud.qdrant.io'` (reproduced 2026-11-21 at 7 s; the same class of error caused 27 transient failures during the original 541-post indexing).
- **Root cause:** Qdrant Cloud sits behind AWS CloudFront; an edge node occasionally serves a TLS certificate whose SANs don't match the requested host. Purely transient — retrying against the same host succeeds (different edge).
- **Fix (in `qdrant()`):** all Qdrant calls **retry up to 3×** on transient failures — cURL codes **28, 35, 52, 53, 56, 60** or remote HTTP **502/503/504** — with backoff `usleep((1+attempt) * 1 s)` (scaleable via `$GLOBALS['ks_backoff_scale']` for tests). All Qdrant operations used by the plugin are idempotent (reads, upsert-by-id, delete), so retrying is safe. If TLS errors persist through all attempts, the error is rewritten to a clear **`ks_qdrant_tls`** message (HTTP 503): "intermittent … clears on its own — try again in a few seconds."
- **Invariants (do not regress):**
  - The retry loop + transient code list in `qdrant()` must stay; removing it returns users to raw cURL 60 failures on every edge glitch.
  - Keep idempotency-safe assumptions: if you add a **non-idempotent** Qdrant call, it must bypass the retry or be made idempotent.
  - Keep the `ks_qdrant_tls` rewrite so users get guidance instead of a raw cURL message.
- **Guards (tests/smoke.php):** `Retry transient Qdrant TLS error and recover` and `Report a persistent TLS mismatch with guidance` (mock hook `$GLOBALS['flaky']`).

## 4. Apply All Links — HTML anchor insertion safety

- **Risk (if regressed):** wrapping anchor text in `<a>` can produce broken markup (nested/unclosed tags, links inside links, block-level tags inside anchors) when the anchor span starts or ends inside an inline tag or crosses a `<p>` boundary — e.g. anchor `hard all day` over `<strong>hard</strong> all day`, or `spot y` over `spot</em> y`.
- **Fix:** the span matcher (`find_anchor_span()` → `is_tidy_span()` → `nesting_ok()`/`tag_stack()`) only returns a span that is (a) not inside a tag at either end (last-`<`/first-`>` checks), (b) contains no block-closing tag, (c) contains and overlaps no `<a>`, (d) nesting-consistent: the seeded tag stack opened **before** the span must balance identically **after** the span (a tag opened before the span closing inside it, or opened inside it and left unclosed, both break the markup and are rejected). Unplaceable anchors are **skipped and reported, never forced**.
- **Invariants (do not regress):**
  - **The PHP and JS implementations are mirrors.** `admin.js` has `findAnchorSpan` / `spanNesting` / `tagStackScope` implementing the same guards. Any change to the guards **must be made in both files** and verified with both suites: `php tests/smoke.php` (span checks) and `node audit/js-span-test.js` (runs the shipped admin.js code against the same vectors).
  - The join pattern `(?:\s|<[^>]+>)*` between anchor characters is what lets the anchor match across inline tags; keep it in both.
  - **Protected markup is opaque** (added by #6): `<script>`, `<style>`, and HTML-comment ranges — including an unclosed tag stretched to end of content — are computed with the identical regex in both engines (`protected_ranges()` / `PROTECTED_RE` + `protectedRanges()`), and no span may start, end, include, or bridge across such a range. Extend both engines' ranges together; a one-sided change silently desyncs what each engine refuses.
  - Never "force" an insertion when guards reject it; the skip list in the response/UI is the contract. Span validity rests on both engines agreeing — one-sided changes silently desync the editor-side and server-side insertion.
- **Guards:** the matcher, apply, and per-cause skip vectors in `tests/smoke.php` and their mirror in `audit/js-span-test.js` (including the WP 7.1.5 protected-markup vectors and the stubbed block-editor harness — see #6), plus `audit/e2e-apply.php` (live, on a throwaway draft post).

## 5. Development notes for this plugin

- **Environment (DevKinsta):** host PHP 8.4 cannot reach the DB — run all WordPress/DB/Qdrant work with `docker exec devkinsta_fpm php …`; container PHP is **7.4** (no arrow functions / str_contains / PHP 8 syntax in shipped code). Site: `/www/kinsta/public/dev-site` (volume-mounted, host edits are live in the container).
- **Code style of `class-knowledgespark.php`:** dense — **1-space indentation per level, no blank lines**. The `read`/GUI display adds one column; byte-check with `od -c` or a PHP `substr` dump before exact-match edits (exact-match edits have failed repeatedly against display indentation).
- **Whole-file rewrite hazard:** `file()` keeps trailing `\n`; combining it with `implode("\n", …)` doubles every newline (blank line inserted between every line). If a script rewrites the class file, read with `FILE_IGNORE_NEW_LINES`.
- **Testing conventions (tests/smoke.php):** standalone, no WP boot — mocks live at the top (`WP_Error`, `wp_safe_remote_request`, `$GLOBALS` hooks: `index_test`, `flaky`, `ks_format_fail`, `ks_backoff_scale`, `fail_write`). Everything beyond the mocks must keep working; the suite is the regression gate.
- **Live checks (do for provider-facing changes):** repeated runs are required — both failure modes above are *intermittent*. A single successful live run does not prove a fix; a single failure does not disprove current code. Compare `usage.reasoning_tokens` / `finish_reason` when diagnosing AI issues (`audit/ai-format-probe.php`, `audit/ai-repeat-probe.php` replicate the production payload and dump raw provider responses).
- **Provider quirk (validated 2026-11-21):** river.ai GLM-5.3-Flash accepts but **ignores** `thinking: {type: "disabled"}` and `response_format: json_object` works. Do not build logic on the assumption that thinking can be turned off.

## 6. Apply All Links — every anchor "was not found in the current draft" on html-block posts (WP 7.1.5)

- **Symptom (user sees):** in the Gutenberg editor, clicking Apply All Links on a post whose article is a single `core/html` block (this site's standard content shape) reports `No links could be inserted at their suggested anchors.` and every suggestion says `its anchor was not found in the current draft` — even when the anchor text is verbatim in the draft. Reproduced 2026-11-21 on post 410: 5/5 anchors failed.
- **Root cause (three verified defects, found in that order):**
  1. **Dead block-content accessor.** WordPress 7.1.5 registers the text attribute as `content` for `core/html`, `core/paragraph`, `core/list-item`, `core/freeform` (verified in-container via `WP_Block_Type_Registry` — no `innerHTML` key exists). `applyViaBlockEditor()` read only `block.attributes.innerHTML` → the search string was always `''` → no anchor could ever be located. Older block schemas used `innerHTML`; some intermediate ones use `value`.
  2. **Protected-markup susceptibility (latent, activated by fixing 1).** The span matcher matched **inside** `<script type="application/ld+json">` schema markup: headline/FAQ text is a verbatim copy of body text and sits at the top of the html block, so it wins document order. A span fully inside a `<script>` body passed every pre-fix guard — and would have injected `<a>` into the JSON-LD on the first successful apply, silently breaking structured data. Proven 2026-11-21 by running the shipped matcher against post 410's actual structure.
  3. **Misleading skip message.** Anchors whose only occurrence sits inside an existing link were correctly rejected by the anti-nested-link guard (the draft links those phrases to the production mirror `jarhabitats.com`, which `url_to_postid()`'s exclusion map cannot see) but were reported as "not found".
- **Fix (change `fix-apply-all-links-on-wp7`, verified 2026-11-21):**
  - `applyViaBlockEditor()` resolves the text attribute from the chain `innerHTML` → `value` → `content` (first string-valued key) and writes the result back under **the same key it read**.
  - Both matchers pre-scan protected ranges — `<script …>…</script>`, `<style …>…</style>` (stretched to end-of-content when the tag is unclosed), and `<!-- … -->` — with an identical regex, and reject any candidate span that overlaps one. Each rejection carries its reason (`in_link` / `in_protected` / `untidy`; PHP out-param, JS `hint` field), so the engine that dies knows why.
  - Skip sentences use one fixed taxonomy in both engines: not in the current draft / already inside a link / only inside script, style, or comment markup / crosses formatting that cannot be wrapped safely. "Not in the current draft" is reserved for genuinely absent text.
- **Invariants (do not regress):**
  - The ordered attribute chain plus same-key write-back is the cross-version contract. **Never reintroduce a single hard-coded attribute name.** Diagnostic when apply-wide failures recur: diff `wp-includes/blocks/*/block.json` attribute names in the container first.
  - The protected-range regex and the overlap rule must stay identical between `protected_ranges()` (PHP) and `PROTECTED_RE` / `protectedRanges()` (JS) — change both together.
  - Both engines report the same sentence per cause; found-but-unplaceable text must never render as "not in the current draft".
  - The inserted `<a>` keeps its `title` attribute (tests assert the exact saved markup) — do not drop it.
- **Guards (offline: `tests/smoke.php` 49 checks, `audit/js-span-test.js` 35 checks):** matcher vectors for inside-script (JSON-LD shape), inside-style, inside-comment, bridged-across-script, unclosed-script over-mask (2), body-preferred positive with script byte-identical after insertion, per-cause `api_apply` sentences, and the stubbed block-editor harness (attribute chain: `content`-only / both-keys-prefers-`innerHTML` / no-key-skips; mixed and all-fail skip causes; JSON-LD left byte-identical). Live check (DevKinsta, throwaway draft post, deleted after): plain anchor wrapped and saved, JSON-LD byte-identical before/after, already-linked and JSON-only anchors skipped with their honest sentences.
- **Open follow-up (separate change, deliberately not fixed here):** cross-domain mirror awareness at suggest time (the AI still picks anchors inside production links because the exclusion map cannot see `jarhabitats.com` URLs), and a placeability pre-check in `rank()` so unplaceable anchors never reach the UI.
- **Ownership note (2026-11-21):** the WP 7.1 raw-block data-layout class and the entity gap on this site's current WordPress are owned by entry #7 (change `fix-apply-all-links-on-wp71`); the attribute-chain contract above is extended, not replaced, by it.

## 7. Apply All Links — WP 7.1.5 raw-block (`core/html`) data layout + entity gap

- **Symptom (user sees):** in the Gutenberg editor, clicking Apply All Links on a post whose article is one `core/html` block (post 409, reproduced 2026-11-21 after the fix in entry #6 shipped) reports `No links could be inserted at their suggested anchors.` and every suggestion says `its anchor is not in the current draft.` — even though the anchor text is visibly in the article. Nothing is changed and no save happens (zero placements → no save).
- **Root cause (two verified causes, in this build):**
  1. **Raw blocks lost their attribute channel in WP 7.1.** `core/html`'s `content` attribute is deprecated since 7.1 ("alternative: inner content"): this build's parser resolves source-less attributes only from the block comment (`<!-- wp:html -->` carries none), the block's own editor component strips any legacy `content` attribute into `innerContent` on load, and `save()` returns null. The article lives only in the block's **inner content** (`innerContent`/`innerHTML`), in no attribute. The attribute-reading apply path (entry #6 fix) therefore saw empty content and every suggestion fell to the generic skip sentence — honest, but misdirecting.
  2. **Entity gap (latent).** Suggest-time validation matches anchors against entity-decoded text, but both span matchers compared character-for-character against raw HTML where `&` is stored as `&amp;` — an AI anchor containing `&` (post 409 has four such headings) would fail even with the reader fixed.
- **Fix (change `fix-apply-all-links-on-wp71`, verified 2026-11-21):**
  - The editor apply path reads raw blocks (`core/html`, `core/freeform`) from inner content when no readable attribute exists — legacy attribute chain first, then `wp.blocks.getBlockContent`, then `block.innerHTML`, then `innerContent` joined; classic text blocks keep the attribute-chain behavior unchanged, and the chain stays the cross-version fallback (see entry #6).
  - The raw-block write mirrors the core Custom HTML modal exactly: re-parse `<!-- wp:{name} -->\n{content}\n<!-- /wp:{name} -->`, then `updateBlock(id, {innerContent})` plus `replaceInnerBlocks(id, kids, false)`; falls back to a full-object `replaceBlock` (innerContent) when the modern dispatchers or `wp.blocks.parse` are absent, and to the same-attribute write only on stores without `innerContent`.
  - Both engines tokenize anchors with per-character entity alternatives — named `amp`/`lt`/`gt`/`quot`/`apos`, decimal numeric, lowercase hex — plus a no-break-space form for the space character and nbsp in the joiner; a resolved span is always the raw slice, so stored entities are byte-preserved.
  - Admin script/style version bumped 0.0.1.3 → 0.0.1.4 for cache busting.
- **Invariants (do not regress):**
  - **Never make one hard-coded source the sole truth for raw blocks** (extends entry #6's chain contract): attributes remain the legacy fallback and inner content the current channel; keep both present.
  - The entity token table and the joiner must stay byte-aligned between `find_anchor_span()` (PHP) and `findAnchorSpan` (JS) — change both together (mirror rule, entry #4). Hex entities match lowercase forms only — a documented corner.
  - The only document change an apply makes is the `<a>` wrap itself; no entity is ever normalized, rewritten, or expanded.
  - The editor path stays frontend JS + `savePost()` — the save button invocation the product direction calls for.
- **Guards (offline: `tests/smoke.php` 62 checks, `audit/js-span-test.js` 56 checks):** entity vectors in both engines (ampersand/nbsp/apostrophe/angle forms, decimal+hex, in-attribute unresolvable, plain anchors unchanged); WP 7.1-style raw-block fixtures in the stubbed harness (inner-content read, `updateBlock(innerContent)`-only write, no `content` attribute created, accumulation across placements, `replaceBlock` fallback, JSON-LD byte-identical); REST `api_apply` vector proving raw `&amp;` bytes survive the saved document. Live checks: the shipped block-editor code applied 5/5 anchors in post 409's real document inside a 7.1.5-shaped store (node), and a container probe on a throwaway draft (real `api_apply`, five real permalinks) verified persistence in the database before deleting the post.
- **Live-confirmation correction (2026-11-21, later the same day):** the 10:51 "solved" report was a **false positive** — the apply said "Inserted 5 suggested links and saved the post", but the saved content stayed byte-identical to the pre-run content (md5 match, zero links persisted). The reader, channel, and entity fixes above are correct and necessary; the editor write side was dead — writes were addressed to a non-existent `blockId` property. That write-side failure class is owned by entry #8 (change `fix-block-editor-client-id`).

## 8. Apply All Links — false success: "Inserted N links" saved zero links (`blockId` vs `clientId`)

- **Symptom (user sees):** the editor reports "Inserted N suggested link(s) and saved the post." and reloads — but the reloaded article has no new links, and the saved post content is byte-identical to before the apply. Reproduced 2026-11-21 on posts 409 and 405: both saved at the exact apply timestamps with zero links (md5-identical to the pre-run content).
- **Root cause:** the editor apply path addressed every write dispatch (`updateBlock`, `replaceInnerBlocks`, `replaceBlock`) to `block.blockId` — a property that does not exist in the real block-editor store. The store's own code addresses blocks by `block.clientId` (its tree updates read `block.clientId`, and `getBlock` is keyed by it). The dispatches therefore carried an `undefined` client id; the `UPDATE_BLOCK` reducer guards with `if (!state.has(action.clientId)) return state;` — a **silent no-op**. Nothing threw, `placed++` ran anyway, `savePost()` persisted the *unchanged* store, and the UI reported a success that never happened. The stubbed harness had invented `blockId` in the wp7 change and every fixture since stayed self-consistent with the code, so all checks passed while real-editor writes were dead — **a self-consistent fake proves nothing**.
- **Fix (change `fix-block-editor-client-id`, 2026-11-21):** all four write sites address the block's `clientId`; a located block with no client id is never written to and is reported as refused; every dispatched write is **verified by re-reading** the block's content and requiring the inserted `<a href="…" title="…">` wrap to be present before the link counts as placed — any silent no-op now surfaces as `the editor refused this change (…)` instead of a false success. Enqueue versions bumped 0.0.1.4 → 0.0.1.5.
- **Invariants (do not regress):**
  - Address editor blocks only by the store's `clientId` — never by a property name invented by a test fake; validate stub-store contracts against the shipped `wp-includes/js/dist` bundle (the unknown-id no-op is the `UPDATE_BLOCK` reducer case in block-editor.js).
  - **Verify after write**: re-read the block and require the inserted wrap before counting a placement. Never treat a redux dispatch as acceptance — dispatches are fire-and-forget action objects.
  - The harness fakes mirror the real reducer (writes to unknown client ids are silent no-ops, writes to known ids mutate the store), and fixtures cover both the id-less block and the ignored write.
  - A live confirmation requires saved-DB-content proof (md5 changed, links present in `post_content`) — never a UI success message.
- **Guards (offline: `audit/js-span-test.js` 63 checks, `tests/smoke.php` 62 checks):** refusal fixtures — id-less block reported as `(block identity missing)` with nothing dispatched and no save; ignored write reported as `(the editor store did not accept the change)` with the completion message never claiming an insertion; all pre-existing placement fixtures re-verified through the post-write re-read. **Live check (done 2026-11-21, DB-proof standard):** applied in the real editor on post 405 — the container probe proved `post_content` changed (md5 `5e54dade…` → `1ccc607b…`) with 4 titled links persisted to real targets (253, 302, 242, 282); the user confirmed the links in the editor. Post 409 stays linkless by user choice (its earlier dead runs saved identical content); apply there anytime.

## 9. Agent tools — abilities registration is the only agent surface (no protocol code)

- **Change (`add-agent-interlink-tools`, 2026-11-21):** the two editor-button actions are published as four WordPress abilities on the core Abilities API — `wp_register_ability` on `wp_abilities_api_init`, category `knowledgespark` on `wp_abilities_api_categories_init` (core since 6.9; the dev-site's 7.1.5 also lists public abilities over `/wp-json/wp-abilities/v1`): find-suggestions, apply-all-links, interlink, list-posts. Agents reach them through WordPress MCP plugins — MCP Adapter over HTTP at `/wp-json/mcp/mcp-adapter-default-server` with Application-Password Basic auth (initialize → session header → `tools/call` with `mcp-adapter-execute-ability`) — or the core abilities REST route. A new off-by-default `agent_access` setting filters `wp_is_application_passwords_available` to `true` on plain-HTTP sites only when an administrator opts in (the dev-site's `http://dev-site.local` needs it; HTTPS sites never do).
- **Invariants (do not regress):**
  - **Ability callbacks are thin reuses, never a second implementation.** `ability_suggest`/`ability_apply` call `api_suggest`/`api_apply` with the same request shape the REST routes receive; permission callbacks mirror the REST permissions exactly (`edit_post` on the target post, `edit_posts` for listing). Guard parity and the per-cause skip taxonomy are automatic — never fork engine logic into an ability path.
  - **No protocol code ships in the plugin.** MCP exposure is opt-in via `meta.public => true` only; discovery, sessions, and transport belong to MCP Adapter and core. Registration is guarded by `function_exists` — on WordPress without the Abilities API it is a silent no-op and the editor/REST behavior is unchanged.
  - **The interlink ability mirrors the button pair:** it filters to applicable suggestions (non-empty anchor + valid `http(s)://` URL — the same filter the Apply All Links button applies) before calling apply, applies nothing when nothing is applicable, and merges per-cause skips into its report.
  - **The app-password opt-in is inert by default and on HTTPS:** the filter returns the core value unchanged when the setting is off; enabling it on a public plain-HTTP site is an explicit, warned administrator decision.
- **Guards (offline: `tests/smoke.php` 117 checks):** registration vectors (exactly four abilities under the plugin category with schemas, public flags, callable callbacks, and zero registration when the API is absent), suggest/apply parity vectors, listing visibility and cursor-paging vectors, interlink composition vectors (applicable filter, per-cause skips, nothing-applicable, no save), permission-refusal vectors, and opt-in availability vectors. **Live check (done 2026-11-21, DB-proof standard):** through MCP Adapter over HTTP on the dev-site — initialize handshake, discovery listed the four abilities, `find-suggestions` returned 5 AI-reviewed suggestions (26 s), `interlink` applied 5/5 links (28 s), and the container probe proved `post_content` changed (md5 changed, 5 target links persisted); the throwaway post and Application Password were deleted afterward. Environment note for future probes: the dev-site's php-fpm ships xdebug (`start_with_request=yes`) and a small worker pool — stuck workers from an earlier session can wedge the pool and 504 every new endpoint; recycle the php-fpm workers before blaming a new route.

## 10. Bulk indexing — batch-of-100 embedding and the background job (0.0.3)

- **Change (`background-batch-indexing`, 2026-11-21):** the admin "Index published posts" button no longer loops one post per REST call from the browser (which had to keep the page open and cost ~2 Qdrant HTTP calls per post — 1,082 calls for the original 541-post indexing, exposed to the #3 transient failures). It now starts a resumable background job: `api_index` validates the collection, persists a fresh `knowledgespark_index_job` option state (status/cursor/totals/errors capped at 20/timestamps), schedules the `knowledgespark_index_batch` single event and `spawn_cron()`s it; the chained cron event processes batches of 100 posts — one `POST /points` payload retrieve for the whole batch's IDs plus one `PUT /points?wait=true` upsert carrying only stale points as `{id, vector: {text, model}, payload}` inference objects (120 s timeout) — looping within a 20 s time budget per run, and it schedules its successor (+60 s) **before** working so a PHP kill mid-run can never strand the chain. New REST routes `status` and `stop` (both `manage_options`); `admin.js` polls status every 3 s instead of driving batches; `api_reset` stops a running job before deleting the collection.
- **Invariants (do not regress):**
  - **A batch of ≤ 100 posts costs at most one payload retrieve and one inference upsert, both through the unchanged `qdrant()` retry wrapper** (read + idempotent upsert-by-id = retry-safe; the cURL/HTTP transient list, the `ks_backoff_scale` test hook, and the `ks_qdrant_tls` rewrite all apply to batch calls).
  - **The fingerprint/legacy skip logic is shared, not forked:** `point()` + `stored_current()` are the only builders of fingerprints, payloads, and upsert points, used by both the single-post `sync()` (save-time WP-Cron path, semantics unchanged) and the batch runner — never reimplement the profile/fingerprint formula (it contains the literal `'\n'` separators from `profile()`, which are part of every stored fingerprint).
  - **Deletion race guard:** every post is re-checked published/public right before it joins the upsert; a post deleted after the batch's IDs were fetched is removed (`remove()`) and never resurrected. Failed batches record the post-ID range + cause, advance the cursor, and leave `_ks_sync_error` set per post — one bad batch must never stall the run.
  - **Stop is honored at batch boundaries:** the runner exits unless the persisted status says `running`; `stop` sets `stopped` and clears the scheduled event; reset stops the job first; a fresh start after done/stopped re-verifies and skips unchanged posts.
  - **Cron chain facts (verified against the shipped WordPress 7.1.5 source):** `spawn_cron()` is a no-op inside wp-cron.php (`DOING_CRON` guard at `wp-includes/cron.php`), so the chain advances because core hooks `_wp_cron()` onto `shutdown` of every ordinary request (including the settings page's 3 s status polling), and the pre-scheduled successor guarantees no stranding; on zero-traffic sites a system cron entry keeps runs moving (readme documents it).
- **Guards (offline: `tests/smoke.php` 159 checks):** batch vectors (100-post batch = one retrieve + one upsert, exactly the stale points upserted, current/legacy points skipped without an upsert, mid-batch deletion not resurrected, 250 posts looped in one run = 6 Qdrant requests), failure-accounting vectors (retrieve failure fails the batch with ID range + per-post meta, upsert failure fails only the attempted points, the cursor still advances), lifecycle vectors (prompt start that persists/schedules/spawns, idempotent start while running, fresh pass after done, idle/running status exposure with no Qdrant calls, stop + runner honors it, reset stops the job first), and transient-retry vectors (a flaky TLS call recovers; persistent TLS reports the guidance message). **Live check (done 2026-11-21, container probes + HTTP on the dev-site):** start returned in 1.4 s with no batch work inline; a full 541-post background run (settings page never open) completed in ~2 minutes — 536 indexed, 5 legacy-skipped, 0 failed, exactly 6 batches at ~2 Qdrant requests each; a re-run then skipped all 541 by fingerprint and the collection count endpoint confirmed 541 stored points. `status`/`stop`/`index` REST routes exist and return 401 unauthenticated. Stop was honored at a batch boundary (a stopped job ignored a directly invoked runner and the event was cleared). **Loopback observation:** core's `spawn_cron()` sets the `doing_cron` transient lock for its 60 s window before dispatching — when that loopback is dropped (observed once from a CLI probe), the first due event is processed by the next `wp-cron.php` hit after the lock expires, so batch #1 can start up to ~60 s late; the pre-scheduled successor makes mid-run kills recover the same way, and `curl http://<site>/wp-cron.php` (verified 200) or a system cron entry always restarts the chain.
